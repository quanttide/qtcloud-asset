# 作者的产品潜意识

从 asset-agent 对话过程中推测出的 8 个一致性特征。

**1. 敏捷是底线，不是选项**

任何看起来像瀑布的模型都会被触发修正。不是因为瀑布不能用，而是对"让角色自治"有不可妥协的坚持。

**2. 技术是手段，业务是标准**

每个抽象都要能翻译成角色在真实工作中的决策权。不能翻译的，再漂亮也不要。每次问技术方案都回答"不够业务"。

**3. 减法直觉**

9 个 agent 砍到 3 个，事件面板砍掉，详情面板砍掉。加功能的提议回应总是砍。默认"少一个视图比多一个视图好"。

**4. 图是诊断工具，不是展示工具**

反复调布局不是为了审美，而是因为"直线重叠"说明看不出瓶颈。图要回答的问题是"哪里卡住了"，不是"看起来怎么样"。

**5. 读者意识强**

user.md 重写了三次。第一次像运维文档被否决，第二次像产品文档继续打磨，第三次变成团队适配指南才满意。因为在意谁在看。

**6. 自己就是 QA**

"右侧空白了"、"没有资产"、"直线重叠"——体验缺陷自己找出来，零容忍。

**7. 契约先于代码**

每次操作前先读 `.quanttide/` 文件。相信显式规则比隐式默契可靠，相信写下来的东西才会被执行。

**8. 要真实不要演示**

不满足于捏数据，要求从真实目录生成。要版本节点，要 src 目录结构。验证标准是"放到真实场景中不会崩"，不是"demo 跑通了"。

—

总结：做的不是一个展示智能体的工具，而是一个诊断协作效率的镜子。关心的不是智能体有多智能，而是它们之间的协作有没有瓶颈、反馈有没有闭环、迭代有没有收敛。

## 当前结论

**关于产品方向**

- 做的不是智能体展示工具，而是协作效率诊断镜
- 图的价值是暴露瓶颈、反馈闭环、迭代收敛，不是好看
- 适合有自治权的团队，不适合统一排期的组织

**关于数据模型**

- 单一图数据源（graphNodes + graphEdges）驱动三视图可行，但事件应从边属性中拆出
- 智能体间触发关系不能靠文件名模式推断（杂散边问题），必须用目录路径 + 所有权双重约束
- 版本节点能表达迭代收敛，但三列对齐同步推进是伪敏捷，需要独立版本线 + 事件驱动交叉

**关于原型状态**

- app.py 可从真实目录 + agent_rules.yaml 生成图数据
- index.html 展示资产结构和智能体拓扑（职责可见）
- evolution.html 展示版本迭代（过程诊断）
- 双页分离已验证可行

**待解决的问题**

- 版本迭代目前仍隐式假设同步推进，未实现独立版本线
- 自迭代（智能体内部版本提升无触发）尚未实现
- 收敛标准是隐式的（无更多反馈），未显式化为数据
