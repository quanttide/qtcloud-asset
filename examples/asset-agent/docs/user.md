# 资产智能体协作壳

三位智能体协作完成一个功能从想法到交付的全过程。

- drd-agent 负责设计
- code-frontend-agent 负责前端
- code-backend-agent 负责后端

它们不排期、不等候，各自按自己的节奏迭代。谁发现问题，谁决定是自己改还是触发别人改。

## 怎么协作

DRD 出设计 → 前后端按设计实现 → 实现中发现设计问题 → 反馈 DRD 修改 → 循环直到没有人再提反馈。

每个智能体的版本号是自己的局部计数器。前端改了个按钮颜色，自己迭代到 v1.1，不需要告诉别人。前端发现缺了退款入口，这不是前端能定的，所以提反馈触发 DRD 改版。什么时候该自己改、什么时候该触发别人，决策权在智能体手里，不在系统里。

## 这个工具回答的问题

- 一个功能迭代了多少轮
- 谁在等谁
- 瓶颈在哪——哪条线上反复出现反馈，说明那个角色一直没做好
- 最终是怎么收敛的——收敛不是"所有人都做到 v3"，而是"所有人都没有再提反馈了"

## 什么团队适合

有自治权的团队。每个角色自己掌握发布节奏，前端可以今天改明天发，后端走自己的部署周期。不需要所有人一起发版、版本号不必一致。

如果你的团队要求统一排期、统一发版，这个模型是过度设计。

## 两个视图的分工

两个页面回答不同的问题。

**资产结构（index.html）** — 职责可见。
看一个业务功能由哪些角色协作完成，每个角色管什么目录、产出什么文件、跟谁有协作关系。回答"这事谁负责、上下游是谁"。

**资产演化（evolution.html）** — 过程诊断。
看这个功能经历了多少轮迭代才收敛，反馈集中在哪条线上。如果前端反复提反馈，说明设计一直没到位。如果后端总在返工，说明需求不明确。回答"协作效率怎么样、瓶颈在哪"。

结构视图回答「做了什么、谁做的」。演化视图回答「怎么做到的、花了多少轮」。只看分工不看演化，不知道效率高低。只看演化不看分工，不知道问题出在谁身上。

## 启动

双击 `index.html` 看到资产结构和协作拓扑。双击 `evolution.html` 看到版本迭代演化。
