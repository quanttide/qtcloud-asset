# 资产版本因果链可视化

## 场景 1：版本关联不可追溯

### 工作角色

- 资产查看者（创始人）

### 问题

触发：在查阅资产仓库时，发现设计文档和代码文件各自更新了多次版本。

现状：每个资产文件在各自目录里独立维护，有文件系统和 Git 记录版本信息，但版本之间没有跨资产的关联标注。

困难：无法回答「前端这个改版对应的是哪版设计」「DRD v2 的修改到底是前端的反馈还是后端的反馈」「现在仓库里各资产的版本之间是什么关系」。

后果：复盘的唯一方式是翻 Git log 和靠记忆，时间长了对不上。新加入协作的人不知道当前各资产之间的对应关系，容易在错误版本的基础上工作。

### 假设

如果存在这样一个平台，能够把不同目录下的资产版本之间的因果关系画出来，让资产查看者一眼看出设计、前端、后端各到了什么版本、谁触发了谁。

## 场景 2：迭代过程不可见

### 工作角色

- 资产查看者（创始人）

### 问题

触发：一个功能开发完成，想知道整个过程花了多少轮迭代。

现状：只能看到最终结果，看不到中间经历了多少次"设计→开发→反馈→设计修改→开发"的循环。

困难：说不清协作瓶颈在哪——是前端反复提反馈说明设计不到位，还是后端总在等设计说明需求不明确。没有数据支撑判断。

后果：协作效率完全靠直觉评价，无法针对性改进。瓶颈在哪、谁在等谁、什么时候收敛的，全都靠猜。

### 假设

如果存在这样一个平台，能够把一次协作的完整迭代过程记录下来并可视化，让资产查看者看清每一轮的触发和反馈路径、最终是在哪一版收敛的。

## 场景 3：收敛状态不明确

### 工作角色

- 资产查看者（创始人）

### 问题

触发：所有人觉得功能做完了，但没有人能确认「真的做完了」。

现状：各角色各自认为自己的工作完成了，但缺少一个全局信号表明所有相关方都没有未处理的反馈。

困难：不知道设计改到第几版才算最终版，前端做到第几版才不用等设计再改，后端是不是还有未处理的反馈。

后果：功能上线后才发现设计文档的版本和实现不匹配。或者反复修订却没人喊停，迭代永不收敛。

### 假设

如果存在这样一个平台，能够在所有相关方都没有未处理反馈时标记为收敛状态，让资产查看者明确知道「这个功能已经合上了，不会再改了」。
