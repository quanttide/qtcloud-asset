# 图数据模型 — 业务假设

文档状态：v1.0 已确认
领域：数字资产管理 × 智能体协作
日期：2026-05-16

---

1. 概述

图数据模型由 `graphNodes` 和 `graphEdges` 构成，是资产智能体协作的数据基础。下面解读该模型隐含的业务假设。

2. 目录结构即组织分工

资产树中的目录层次不是随意命名，它假设：

```
元仓库/         = 企业级战略层，全体资产归属
├── roadmap/    = 战略规划
├── 平台/       = 产品线（single-repo）
│   ├── docs/   = 文档职能
│   ├── src/    = 开发职能
│   ├── test/   = 测试职能
│   └── config/ = 运维职能
├── 示例/       = 内部示例/培训
└── 库/         = 公共基础设施
```

谁管辖哪个目录，谁就对该目录的资产质量负责。业务假设是：**组织分工可以且应该映射为目录结构**，智能体挂载点就是对这种映射的显式声明。

3. 智能体即业务角色

9 个智能体对应软件开发流程中的核心角色：

| 智能体 | 业务角色 | 职责边界 |
|:-------|:---------|:---------|
| meta-agent | 战略规划者 | 制定路线图，下达 PLAN |
| platform-agent | 产品负责人 | 拆解任务，回报状态 |
| drd-agent | 需求分析师 | 产出领域需求文档 |
| code-agent | 开发者 | 实现代码 |
| qa-agent | 质量保障 | 审查设计，编写测试策略 |
| test-agent | 测试工程师 | 执行测试，报告缺陷 |
| config-agent | 运维工程师 | 管理配置 |
| lib-agent | 公共库维护者 | 基础设施和共用模块 |
| example-agent | 内部技术写作 | 编写示例和教程 |

业务假设是：**软件开发流程中的角色可以抽象为智能体**，每个智能体有明确边界，通过文件交换完成协作。

4. 三种边即三种协作方式

| 边类型 | 业务含义 | 线型 | 协作方向 |
|:-------|:---------|:-----|:---------|
| write | 生产者产出成品 | 灰色虚线 | 智能体→资产文件 |
| trigger | 上游通知下游 | 蓝色实线 | 上游智能体→下游智能体 |
| feedback | 下游反馈问题 | 橙色虚线 | 下游智能体→上游智能体 |

业务假设：

- 所有工作成果是**文件**，write 边表达"谁产出什么"
- 上下游协作是**事件驱动的串行传递**，trigger 边表达"你完成了，我开始"
- 反馈是**协作的重要组成部分**，feedback 边表达"这里有问题，请修改"

5. 文件系统即协作总线

整个协作以文件系统为信号载体：

- 事件存储在 `{管辖目录}/.events/{id}.json`
- 智能体监听文件变化决定是否行动
- 没有 IM、邮件、Jira 等第三方协作工具

业务假设：**文件定稿是唯一的协作触发条件**。一个文件从 draft 变为 final，意味着一项工作完成，可以通知下游。这要求团队对"定稿"有共识。

6. 协作链路即业务流程

典型链路：

```
meta-agent → platform-agent → drd-agent → qa-agent ──→ (feedback back)
                                        → code-agent → test-agent ──→ (feedback back)
```

这个链路假设了一个**瀑布+反馈环**的混合流程：

- 战略从上向下分解
- 每一层完成后触发下一层
- 下游发现问题可以反向反馈
- 反馈到达后上游修改，重新触发

7. 关键业务约定总结

| 假设编号 | 假设 | 若不成立的影响 |
|:---------|:-----|:---------------|
| A01 | 组织分工可映射为目录树 | 智能体挂载点失去业务含义 |
| A02 | 角色职责边界清晰 | 智能体之间出现职责重叠或空白 |
| A03 | 协作是串行有向的 | 无法表达并行或多路归并 |
| A04 | 文件是唯一工作产物 | 数据库记录、API 调用等不在模型内 |
| A05 | 文件定稿触发下游 | 如果工作以其他方式结束（如 PR merge），模型不匹配 |
| A06 | 反馈逆着触发链返回 | 跨层级或跨链路的反馈不能被表达 |
