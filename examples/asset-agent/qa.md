# asset-agent 验证计划

## 概述

分 4 个阶段验证资产智能体协作壳的设计可行性。每个阶段验证成功后进入下一阶段，发现问题则调整设计或补充假设。

## 第一阶段：数据模型

验证 `graphNodes` + `graphEdges` 能否表达资产智能体的协作关系。

| 验证项 | 操作 | 通过标准 |
|:-------|:-----|:---------|
| 节点类型覆盖 | 列出当前所有 Dir/Agent/File 节点，检查是否覆盖资产结构 | tree -L 4 输出的目录结构可完整编码为 graphNodes，无遗漏 |
| 边类型覆盖 | 检查 write/trigger/feedback 是否覆盖已知协作模式 | 任选两个智能体，其协作关系可用三条边之一表达 |
| 双端互通 | app.py --output data.js 生成的文件格式与手写 data.js 一致 | diff 两个文件，结构完全一致（忽略具体值） |
| 业务假设 A01-bis | 验证正交触发条件 | 同一目录下多个智能体的 watch glob 互不重叠 |

## 第二阶段：三视图渲染

验证同一数据源能否正确驱动三个视图，且焦点联动同步。

| 验证项 | 操作 | 通过标准 |
|:-------|:-----|:---------|
| 资产树递归 | 打开 index.html，检查左面板目录树 | 所有 Dir 节点正确嵌套，与 data.js 的 parent 链一致 |
| 智能体标签 | 检查目录节点右侧的智能体 badge | `库` 下有智能体时显示"1 智能体"，无智能体时不显示 |
| 关系图过滤 | 检查中央关系图节点 | 只显示 Agent 和 File，不显示 Dir |
| 写入边虚线 | 检查灰色虚线箭头 | write 边的 `from` 是 Agent，`to` 是 File |
| 触发边实线 | 检查蓝色实线箭头 | trigger 边的 `from` 和 `to` 都是 Agent |
| 反馈边橙色虚线 | 检查橙色虚线箭头 | feedback 边的方向和 trigger 相反 |
| 焦点联动 | 点击树节点 → 图节点高亮 → 事件过滤 | 三者同步，不出现选中不一致 |
| 事件时间线 | 点击边的展开按钮 | 显示完整事件 JSON，格式与 CloudEvents 一致 |

## 第三阶段：协作链路

验证 trace-001/002/003 三条注入的模拟链路是否完整可追踪。

| 验证项 | 操作 | 通过标准 |
|:-------|:-----|:---------|
| 链路完整性 | 展开 trace-001 每个事件卡片 | 6 个步骤：meta→platform→drd→qa→drd→code→test |
| 反馈环可视化 | 检查 qa→drd 和 test→code 的反馈边 | 橙色虚线箭头方向正确，点击展开显示 payload |
| 跨层反馈（A07） | 构造一条 test→drd 的跨层反馈事件 | 规则引擎按 target 字段正确路由 |
| 时间排序 | 检查右面板事件列表 | 按时间倒序排列，最新在最上 |
| 冷却期防循环（A08） | 模拟同一 trace 下 5 秒内重复反馈 | 第二条被合并，aggregated: true |

## 第四阶段：真实场景

用真实资产目录和 `agent_rules.yaml` 验证端到端流程。

| 验证项 | 操作 | 通过标准 |
|:-------|:-----|:---------|
| 规则解析 | 编写覆盖所有智能体的 agent_rules.yaml | app.py 能正确解析，不报 warning |
| 边推断 | app.py 根据 watch/outputs 自动生成 trigger 边 | 依赖关系正确，不遗漏也不冗余 |
| 启动体验 | 打开 index.html | 零配置，双击即渲染 |
| 创始人验证 | 创始人亲自操作三视图 | 分工清晰、协作关系可理解、反馈环可追踪 |

## 退出标准

4 个阶段全部验证通过后，asset-agent 的图数据模型和壳程序可交付下一阶段：

- 如果平台项目需要同样的可视化：**复用 graphNodes + graphEdges 结构，前端代码平移**
- 如果需要实时推流：**data.js 退化为种子数据，WebSocket 推送增量事件**
- 如果需要接入 Opencode：**agent_rules.yaml 作为智能体注册表，app.py 作为配置生成器**
